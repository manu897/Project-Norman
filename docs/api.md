# Norman REST API — for Carl-IOS (and the hub)

Norman's HTTP surface has two halves:

- **Read side** — mirrors `Project-Carl-IOS/api/openapi.yaml`. The iOS app uses the same `Node` / `Reading` / `History` shapes whether it's talking to `carl-hub.local` on the LAN or Norman in the cloud. Auth: user JWT.
- **Ingest side** — `POST /v1/hubs/{hub_id}/batch`, the daily HTTPS upload from a Carl hub. Auth: per-hub bearer token. See [ingest-protocol.md](ingest-protocol.md).

The OpenAPI spec is auto-generated by FastAPI:

- Live: `http://localhost:8000/openapi.json`
- Swagger UI: `http://localhost:8000/docs`
- ReDoc: `http://localhost:8000/redoc`

## Endpoints

### Meta
- `GET /health` — liveness probe, no auth.

### Auth (user JWT)
- `POST /v1/auth/register` — email + password → 201 + token.
- `POST /v1/auth/login` — OAuth2 password flow → `{ access_token, token_type }`.

### Hubs (user JWT)
- `GET /v1/hubs` — list hubs the user owns.
- `POST /v1/hubs` — claim a hub. **Response includes `api_token` — shown exactly once. The user provisions this on the hub firmware.**
- `GET /v1/hubs/{hub_id}` — hub metadata + `last_seen_at`.

### Rooms (user JWT)
- `GET /v1/rooms` — every room across the user's hubs.
- `GET /v1/rooms/{room_id}` — one room + its nodes (the room-kind node + any plants assigned to it).

### Nodes — mirror of hub's `/api/nodes/*` (user JWT)
- `GET /v1/nodes?kind=plant|room|camera` — list nodes, with `latest` reading attached. **Omit `kind` to get plant+room only** — this matches Carl's `node_type` enum (plant/room; camera doesn't exist at the hub's API level). Passing `kind=camera` explicitly still works for Norman-only bookkeeping, but that response can't be decoded by the real iOS app's `NodeType` enum.
- `GET /v1/nodes/{node_id}` — one node's current snapshot.
- `GET /v1/nodes/{node_id}/history?range=24h|7d|30d` — downsampled time series (5-min / 1-hr / 6-hr buckets).
- `GET /v1/nodes/{plant_id}/snapshot` — Norman-only convenience; superseded by the embedded `room` field below. Not called by the real iOS app.
- `GET /v1/nodes/{plant_id}/predictions?limit=` — ML output for one plant. Returns `[]` until the ML pipeline runs.

#### Node shape (must match Carl exactly)

Carl's hub grafts a room's ambient reading directly onto each plant node it returns — not a separate lookup. Norman's `NodeOut` reproduces this field-for-field, checked against `CarlApp/Models/Plant.swift`:

```jsonc
{
  "id": "aabbccddeeff",
  "mac": "AA:BB:CC:DD:EE:FF",
  "name": "Bedroom Monstera",
  "node_type": "plant",        // NOT "kind" — enum: plant | room
  "room_id": "living-room",    // empty string "" when unassigned, never null
  "online": true,
  "last_seen": "2026-08-25T00:04:25Z",
  "battery_pct": 86,
  "latest": { "ts": "...", "soil_pct": 42.2, "...": null },
  "calibration": null,
  "room": {                    // present only on plant nodes with a room assigned
    "source": "room-1",        // id of the room node this came from
    "ts": "2026-08-25T00:04:20Z",
    "temperature_c": 21.4,
    "humidity_pct": 55.0,
    "pressure_hpa": null,
    "illuminance_lux": null
  },
  "hub_id": "hub-001",         // Norman-only extra; harmless — Swift ignores unknown keys
  "species": null              // Norman-only extra; not on Carl's hub yet
}
```

`hub_id` and `species` are Norman additions the hub doesn't send. Swift's `Codable` ignores JSON keys it doesn't have a `CodingKey` for, so these are safe to include — but never rename or remove `node_type`, `room_id`, or `room` without checking `Plant.swift` first.

### Ingest (per-hub bearer token)
- `POST /v1/hubs/{hub_id}/batch` — see [ingest-protocol.md](ingest-protocol.md).

## What is NOT here vs. the hub

- `POST /api/setup/wifi` — captive-portal Wi-Fi, hub-only.
- `GET /api/stream` — WebSocket live stream, hub-only.
- `POST /api/nodes` (the hub's plant-provisioning POST) — handled on the hub, then synced to Norman via the next batch.
- Camera image bytes — stay on the hub. (User decision: 2026-06-12.)

## Codegen for iOS

The iOS app codegens a Swift client from the **hub's** `openapi.yaml`. Shared shapes (`Node`, `Reading`, `Calibration`, `History`) appear here unchanged, so the same generated models deserialize Norman responses. Paths differ (`/api/...` on the hub vs. `/v1/...` here) — point the client at whichever base URL is reachable.

The Norman-only additions (`/v1/rooms`, `/v1/nodes/{id}/snapshot`, `/v1/nodes/{id}/predictions`) are extras over the hub's surface — eventually we'd expect them to appear on the hub too, at which point iOS can hit either side identically.
